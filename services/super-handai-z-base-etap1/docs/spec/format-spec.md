# Спецификация формата ТЗ — v2.0
Статус: FROZEN для v1 Light. Расширения — только через новые директивы с явной пометкой.

## 1. Два конца канала (главное правило)

ТЗ путешествует двумя способами, упаковка различается:
- **В чат (через LLM):** во внешней ограде из 4+ бэктиков с меткой `tz`.
  Внутренние блоки RUN/WRITE — обычные 3 бэктика.
- **В агент (через мост/копипаст в UI):** внутренность от `# ЗАДАЧ:` до последнего
  EXPECT/GIT, БЕЗ внешней ограды (мост её срезает автоматически).

Постановщик ошибается дважды, если путает концы: рамка в рамке (цикл 1) или
отсутствие рамки в чате (цикл 2). Правило: не угадывать — следовать образцу.

## 2. Каркас документа (обязательные элементы)

```tz
# ЗАДАЧ: <название>
# META
workdir: new:<имя> | <имя>   # new: — создать (коллизия → <имя>-2); без new — использовать
mode: auto | confirm          # confirm: каждый RUN/RUN_BG подтверждает оператор
on_fail: stop | continue      # поведение после FAIL шага
cycle: N                      # номер оборота цикла (инкремент при повторной работе)

## ШАГ <n>. <осмысленное название>
<директивы>
```

Отказы: нет шагов → ОТКЛОНЕНО; нет workdir → ОТКЛОНЕНО (изоляция обязательна).

## 3. Директивы

| Директива | Синтаксис | Семантика |
|---|---|---|
| `RUN [shell: pwsh\|bash]` | + fenced-блок команды | исполнить в PTY, виден в живом терминале |
| `RUN_BG [shell: ...]` | + fenced-блок + `WAIT stdout: <маркер>` | фоновый процесс, ждёт маркер, гасится при завершении задачи |
| `WRITE <отн.путь>` | + fenced-блок содержимого | записать файл в workdir (НЕ через PTY) |
| `EXPECT <условие>` | после RUN/RUN_BG/WRITE | машинная проверка; без неё RUN = ошибка линтера |
| `ASK <вопрос>` | строка | пауза-вопрос оператору (в auto — только warn) |
| `GIT commit: "<msg>"` | строка | чекпоинт в workdir (init при первом) |
| `NOTE <текст>` | строка | заметка в отчёт; **NOTE-предсказания** — см. §6 |

Обёртка-метка (`tz` первой строкой) срезается парсером автоматически.
Вводные строки GLM до `# ЗАДАЧ:` срезаются мостом автоматически.

## 4. EXPECT — якорь обязан различать успех и провал

Критерий валидности якоря: **что именно исчезнет из stdout, если шаг провалится?**
Нет ответа — якорь негоден (ритуал вместо проверки).

Типы: `exit=N` · `stdout contains:X` (X — с пробелом после двоеточия; тримится)
· `stdout regex:X` · `file exists:<путь>` (путь в workdir).

Слабый якорь — пример ошибки: `EXPECT stdout contains: archive` когда слово
`archive` выводится в ОБЕИХ ветках. Якорь сбывается всегда = не проверка.

## 5. Конец канала и лимиты

- Хвост вывода в отчёте: ≤30 непустых строк, с маркером
  `[обрезано: показано N из M непустых строк]`. Длинные чтения — файлом в
  workdir с последующим чтением порциями.
- Вывод — не улика. ConPTY-канал изредка дублирует/глотает символы («ddocs»).
  **Test-Path прежде, чем вывод стал гипотезой** — любой путь, полученный из
  stdout, верифицируется независимой проверкой.
- Команды — неинтерактивные (`-y`, `CI=1`); после цепочек cmdlet в pwsh —
  `; exit $LASTEXITCODE`.
- Пути — относительные, разделитель `/`, только внутри workdir. WRITE с
  абсолютным/`..` — error.

## 6. NOTE-предсказания (EXPECT для мышления)

Предсказание постановщика обязано пройти через канал: NOTE-строкой **перед**
шагом, внутри ограды. Снаружи — потеряется и не попадёт в отчёт.
Форма: `NOTE: предсказание ПN — что ожидаю; что считать промахом`.
Сверка после отчёта — по ним слово в слово. Предсказание вне канала — не
предсказание.

## 7. Семантика исполнения (FROZEN для Light)

- FAIL шага: `on_fail: stop` → остальные SKIP; `continue` → дальше (доказано
  тестом diag-continue).
- Отмена шага оператором в confirm → SKIP + заметка «отменён оператором»,
  задача продолжается.
- DENY (guard) → задача останавливается всегда, вне зависимости от on_fail.
- GIT commit: «nothing to commit» — заметка, не провал. WRITE-шаги в отчёте —
  exit=0.
- Стоп оператором → немедленный kill активного PTY + фоновых, статус STOPPED,
  отчёт генерируется.

## 8. Защита от себя (чек-лист постановщика)

1. ТЗ в чате — только с рамкой 4+ бэктика; в агент — срезанная внутренность.
2. У каждого RUN — EXPECT, различающий успех/провал.
3. Команда с выводом >30 строк — писать в файл и читать порциями.
4. Путь из stdout — Test-Path до гипотезы.
5. NOTE-предсказания — до шагов, внутри ограды.
6. Неинтерактивность всех команд; pwsh-цепочки — с exit $LASTEXITCODE.
7. workdir — всегда; повторная работа — существующее имя, cycle+1.

## 9. Известные ограничения Light
- Парсер не поддерживает RUN внутри WRITE-блоков (вложенные ограды 3+4).
- Один RUN = одна команда-цепочка; условная логика — на стороне постановщика
  (несколько RUN или bash-скрипт файлом).
- ЗАМЕТКИ отчёта — только системные; заметки шагов остаются под шагами.
