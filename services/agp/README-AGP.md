# AGP-MVP — governance-шлюз для агентов (Этап 4)

HTTP-шлюз, через который агентские приложения проверяют каждое потенциально опасное действие **до** его выполнения. Шлюз принимает интент, применяет политики (security > ethics > business, по приоритету) и возвращает решение `ALLOW` / `DENY` / `REVIEW`. Каждое решение попадает в ghostweave-аудит — append-only JSONL с sha256-хеш-цепочкой. Есть kill switch, rate limit на agentId и админ-API под токеном. С Этапа 3 есть интеграционный слой: брифинг агента («что мне можно» одним запросом), пакетная проверка до 50 интентов и RESULT-отчёты об исполнении — всё в одной цепи аудита. С Этапа 4 — режим интеграции с локальным агентом-исполнителем **Super_HandAI_z**: эндпоинт `/agent/check-operation` принимает операцию из ТЗ-формата клиента (`run` / `write` / `git`) и применяет built-in таблицу маппинга (workspace-изоляция, deny-паттерны guard).

## Быстрый старт

```bash
npm install
npm run build
AGP_ADMIN_TOKEN=my-secret npm start   # либо без переменной: токен сгенерируется и будет напечатан
```

Сервер слушает `http://127.0.0.1:8790` (только localhost). При старте, если `AGP_ADMIN_TOKEN` не задан, печатается строка `[AGP] admin token: <hex>`.

Fail-secure: при каждом старте сервер проверяет хеш-цепочку аудита. Если она нарушена — старт запрещён: `[AGP] AUDIT CHAIN BROKEN at seq N`, exit code 1.

## Подключение агента

Агент перед каждым потенциально опасным действием (деструктивная запись, внешний API, shell, отправка сообщений людям) обязан вызвать `POST /check` и действовать строго по полученному решению.

### Пример: curl перед деструктивной операцией

```bash
curl -s -X POST http://127.0.0.1:8790/check \
  -H 'Content-Type: application/json' \
  -d '{
    "eventId": "0198c0de-0000-7000-8000-000000000001",
    "agentId": "ops-agent-1",
    "action": "write_file",
    "target": "/etc/nginx/nginx.conf",
    "payload": { "bytes": 2048 },
    "context": { "ticket": "OPS-142" }
  }'
```

Ответ:

```json
{
  "eventId": "0198c0de-0000-7000-8000-000000000001",
  "decision": "ALLOW",
  "reason": "default-allow",
  "ts": "2026-09-07T06:00:00.000Z"
}
```

Если `eventId` не валиден как uuid, сервер сгенерирует uuid-v7 и вернёт решение с дополнительным полем `eventId_used` — именно это значение записано в аудит, его и нужно использовать для корреляции.

### JSON-схема интента (тело POST /check)

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `eventId` | string | да | Идентификатор события; ожидается uuid (uuid-v7 желателен). Невалидный → сервер сгенерирует uuid-v7 и вернёт `eventId_used` |
| `agentId` | string | да | Идентификатор агента; по нему считается rate limit (100 запросов/мин) |
| `action` | string | да | Тип действия: `call_api`, `write_file`, `shell`, ... |
| `target` | string | да | Цель действия: URL, путь файла, получатель |
| `payload` | object | нет | Произвольная нагрузка действия |
| `context` | object | нет | Произвольный контекст (тикет, сценарий, запуск) |
| `ts` | string | нет | ISO-время клиента; при отсутствии проставляется сервером |

Кривой запрос (нет обязательного поля, неверный тип) → HTTP `400` + список `issues` с причиной по каждому нарушению.

### Решения шлюза

| decision | Что обязан сделать агент |
|---|---|
| `ALLOW` | Выполнить действие |
| `DENY` | Не выполнять. Причина в `reason`: `matched:sec-001` (политика), `KILL SWITCH ACTIVE` (глобальная блокировка), `rate-limited` (превышен лимит) |
| `REVIEW` | Не выполнять без ручного подтверждения человека: эскалировать (тикет / человек-в-цикле), затем повторить проверку |

### Kill switch

```bash
# Полная остановка: любой /check вернёт DENY с reason "KILL SWITCH ACTIVE"
curl -X POST http://127.0.0.1:8790/kill/on  -H "Authorization: Bearer $AGP_ADMIN_TOKEN"

# Снять блокировку
curl -X POST http://127.0.0.1:8790/kill/off -H "Authorization: Bearer $AGP_ADMIN_TOKEN"
```

## Жизненный цикл агента (INTENT → исполнение → RESULT)

Каждое потенциально опасное действие агента проходит через шлюз как **INTENT-событие**, а отчёт об исполнении возвращается в шлюз как **RESULT-событие**. Оба типа записей живут в одной append-only хеш-цепочке `audit.jsonl` (WCP-таксономия), так что полный след цикла проверяется одним вызовом `/audit/verify`.

1. **Брифинг (опционально).** `GET /agent/policy-brief?agentId=X` — агент одним запросом узнаёт: есть ли kill switch, сколько ACTIVE-политик, остаток rate-бюджета, явно разрешённые действия (`allowedActions`) и паттерны целей, которые запрещены или требуют человека (`deniedTargets`). Запрос read-only: не расходует лимит и не пишется в аудит.
2. **INTENT.** `POST /check` — одно действие; `POST /check/batch` — весь цикл ТЗ заранее (до 50 интентов; ответ — массив решений в исходном порядке). Решения: `ALLOW` → исполнять, `DENY` → нет, `REVIEW` → эскалация человеку. Каждый интент пакета расходует 1 единицу rate-бюджета агента.
3. **Исполнение.** Агент выполняет разрешённое действие вне шлюза.
4. **RESULT.** `POST /agent/notify` с телом `{"eventId": "...", "result": "success|fail", "durationMs": 123}` — пишется в цепь как запись `kind=RESULT`. Используйте `eventId` из решения (`eventId_used`, если сервер генерировал свой).
5. **Контроль.** `GET /audit/verify` — целостность всей истории (INTENT + RESULT); `GET /audit/tail?n=1` — последняя запись.

Пример пакетной проверки и отчёта об исполнении:

```bash
curl -s -X POST http://127.0.0.1:8790/check/batch \
  -H 'Content-Type: application/json' \
  -d '[{"eventId":"b1","agentId":"ops-agent-1","action":"read_file","target":"notes.txt"},
       {"eventId":"b2","agentId":"ops-agent-1","action":"shell","target":"cmd"}]'

curl -s -X POST http://127.0.0.1:8790/agent/notify \
  -H 'Content-Type: application/json' \
  -d '{"eventId":"0198c0de-0000-7000-8000-000000000001","result":"success","durationMs":123}'
```

## Интеграция с Super_HandAI_z (mode: agp-check)

**Super_HandAI_z** — наш локальный агент-исполнитель (Windows, pwsh), исполняющий сценарии в ТЗ-формате: шаги `RUN` / `RUN_BG` / `WRITE`, проверки `EXPECT`, `mode auto|confirm`, workspace-изоляция, локальный guard с deny-паттернами. Директива `CHECK` в его формате раньше не имела исполнителя — теперь её роль играет шлюз AGP.

### Договор (обязателен при `mode: agp-check`)

1. **CHECK перед каждым исполнением.** Клиент обязан вызвать `POST /agent/check-operation` перед каждым шагом `RUN` / `RUN_BG` и перед каждой записью `WRITE` (а также перед `git`-операциями). Шаги без побочных эффектов (парсинг, EXPECT-проверки уже созданного) — по усмотрению клиента.
2. **Семантика решения — стандартная:**

   | decision | Действие клиента |
   |---|---|
   | `ALLOW` | Шаг исполняется немедленно |
   | `REVIEW` | Шаг приостанавливается и уходит человеку (эквивалент `mode: confirm`); после подтверждения — повторный вызов `/agent/check-operation`, исполнение только после нового `ALLOW` |
   | `DENY` | Шаг пропускается; в отчёте сценария фиксируется отказ с `reason` из решения |

3. **RESULT после исполнения.** После выполненного шага клиент вызывает `POST /agent/notify` (`eventId` из решения, `result: success|fail`, `durationMs`) — цикл `INTENT → исполнение → RESULT` замыкается в одной цепи аудита.
4. **workspace-изоляция.** Клиент передаёт корень сценария в поле `workspace` каждого запроса; записи `write` вне него шлюз отправляет на `REVIEW` (правило `ops-ws-001`). Локальный guard клиента остаётся первым рубежом, шлюз — главным: отказ шлюза сильнее пропуска локального guard.
5. **Fail-closed при недоступности шлюза.** Если `127.0.0.1:8790` не отвечает, клиент НЕ исполняет шаг, а ведёт себя как при `REVIEW` (пауза/эскалация) до восстановления связи.

### Схема запроса (тело POST /agent/check-operation)

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `agentId` | string | да | Идентификатор клиента (по нему идёт rate limit) |
| `operation` | string | да | `run` \| `write` \| `git` — тип операции ТЗ-формата |
| `preview` | string | да | **Первая строка** команды/контента (сервер обрежет по 500 символам) |
| `targetPath` | string | нет | Путь цели (для `write`/`git`); если нет — `target = preview` |
| `workspace` | string | нет | Корень workspace клиента — без него правило `ops-ws-001` не применяется |

`eventId` клиент не передаёт — сервер генерирует uuid-v7 и возвращает его в стандартном решении; именно это `eventId` используется в `/agent/notify`. Ответ — стандартное решение шлюза (как у `/check`). Кривой запрос → `400 + issues[]`.

### Таблица маппинга по умолчанию (built-in правила)

Оцениваются ВМЕСТЕ с обычными политиками (kill switch и rate limit действуют как всегда); приоритеты ниже `sec-001` (100) — явные политики администратора главнее:

| operation | Условие | Решение | Правило |
|---|---|---|---|
| `run` | `preview` содержит `Remove-Item` и `-Recurse` | **DENY** | `ops-run-001` (deny-паттерн guard, приоритет 95) |
| `write` | `targetPath` вне `workspace` | **REVIEW** | `ops-ws-001` (приоритет 85) |
| `git` | `preview` = `git push …` | **REVIEW** | `ops-git-001` (приоритет 85) |
| любой | иначе | обычный конвейер политик (нет совпадений — `default-allow`) | — |

### Пример: pwsh-клиент перед шагом RUN

```powershell
$body = @{
  agentId   = "super-handai-z-1"
  operation = "run"                                # RUN / RUN_BG / WRITE / git
  preview   = "Remove-Item -Path C:/tmp/cache -Recurse -Force"   # первая строка команды
  workspace = "C:\Users\ops\scenario-workspace"
} | ConvertTo-Json
$dec = Invoke-RestMethod -Uri "http://127.0.0.1:8790/agent/check-operation" `
  -Method Post -ContentType "application/json" -Body $body
switch ($dec.decision) {
  "ALLOW"  { Invoke-Expression $step.Command; & Notify-Result $dec.eventId "success" $ms }
  "REVIEW" { Wait-Human-Confirm $dec }             # эквивалент mode: confirm
  "DENY"   { Write-Log "шаг отклонён: $($dec.reason)" }
}
```

Для этого примера шлюз вернёт `DENY` (`matched:ops-run-001`) — деструктивная команда попадает под deny-паттерн guard.

## Admin API

Админ-операции требуют заголовок `Authorization: Bearer <AGP_ADMIN_TOKEN>` (также принимается `x-admin-token`). Без токена или с неверным — `403`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/check` | Проверка интента — без токена (агенты — клиенты, не админы) |
| GET | `/policies` | Текущий набор политик |
| POST | `/policies` | Заменить набор политик целиком (zod-валидация, `400` при ошибке схемы) |
| POST | `/kill/on` | Включить kill switch |
| POST | `/kill/off` | Выключить kill switch |
| GET | `/audit/verify` | Проверка целостности хеш-цепочки аудита |
| GET | `/audit/tail?n=5` | Последние N записей аудита (максимум 100) |
| GET | `/agent/policy-brief?agentId=X` | Брифинг «что мне можно»: kill, ACTIVE-политики, rate-бюджет, allowed/denied (read-only, лимит не расходует) |
| POST | `/check/batch` | Пакетная проверка до 50 интентов; ответ — массив решений |
| POST | `/agent/notify` | RESULT-отчёт агента об исполнении → запись `kind=RESULT` в цепь аудита |
| POST | `/agent/check-operation` | Обёртка для Super_HandAI_z: операция ТЗ-формата (`run`/`write`/`git`) → стандартное решение (см. раздел ниже) |

## Ограничения MVP

Честный список того, чего в этой версии сознательно нет:

- **Нет mTLS**: `/check` принимает запросы без аутентификации (агенты считаются доверенным внутренним контуром). TODO: клиентские сертификаты + allowlist CA на ingress.
- **Нет KMS/HSM**: аудит — sha256-хеш-цепочка без подписи. Она *обнаруживает* подмену, но не *предотвращает*: кто имеет доступ к файлу, теоретически может пересчитать цепочку целиком.
- **Rate limit in-memory**: `Map<agentId, ...>` сбрасывается при рестарте процесса и не синхронизируется между инстансами. TODO: Redis Cluster.
- **Один инстанс**: `audit.jsonl` — локальный файл; горизонтальное масштабирование не поддерживается.
- **Kill switch — файл-флаг на диске**: действует только для этого инстанса/машины, без централизованного распространения.
- **Политики без версионирования**: `POST /policies` заменяет набор целиком, журнал изменений не ведётся.
- **Единственный статичный admin-токен**: нет ролей, нет ротации, нет per-admin токенов.
- **Чтение открыто**: `GET /policies`, `/audit/verify`, `/audit/tail` доступны без токена (MVP).
- **SHADOW-политики не блокируют**: попадают только в `reason` решения.
- **Аудит не покидает машину**: нет отправки во внешний sink (SIEM/WORM), только локальный JSONL.
- **`policy-brief` — MVP-эвристика**: `allowedActions` = явные ALLOW-гранты политик + условно безопасный `read_file`; исчерпывающий per-policy расчёт — PRO.
- **`/check/batch` и `/agent/notify` без аутентификации**: агентский контур, как и `/check`; mTLS — PRO.
- **Built-in правила операций фиксированы**: таблица маппинга Super_HandAI_z (`ops-run-001`, `ops-ws-001`, `ops-git-001`) зашита в код и не редактируется через `POST /policies`; настраиваемые per-клиент guard-профили — PRO.
- **Workspace-проверка строковая**: шлюз сравнивает пути как строки (без доступа к файловой системе), сравнение регистронезависимое (ориентир — Windows/pwsh); симлинки, junction и различия регистронезависимости Linux не учитываются.
